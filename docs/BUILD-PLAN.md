# ShootOps — תוכנית בנייה ל-Claude Code

**איך משתמשים בזה:** כל פאזה = session נפרד. מדביקים את הפרומפט, נותנים ל-Claude Code לעבוד,
מריצים את קריטריוני הקבלה, ורק אז עוברים לפאזה הבאה.

**אל תדביק את כל התוכנית בפרומפט אחד.** זה ייצור 8,000 שורות שאף אחד לא סקר, עם באג
במכונת המצבים שיתגלה רק כשהצלם הראשון יתלונן. הסדר כאן הוא לא עניין של נוחות — כל פאזה
נשענת על זו שלפניה **ועל הבדיקות שלה**.

**לפני הכל:** שים את `CLAUDE.md` בשורש הריפו ואת `docs/` + `db/schema.sql` במקומם.
כל פרומפט מניח שהם קיימים.

## פאזה 0 — שלד ומכונת המצבים ⚠️ הפאזה הכי חשובה

זו הפאזה שקובעת אם המערכת תעבוד. **אין בה UI בכלל.** אם אתה מתפתה לדלג עליה — אל.

```
קרא את CLAUDE.md ואת docs/MVP-SPEC.md.

הקם פרויקט Next.js (App Router) + TypeScript + Drizzle + Postgres מקומי ב-Docker.
הרץ את db/schema.sql וייצר ממנו את הטיפוסים.

עכשיו בנה שני דברים בלבד, בלי שום UI:

1. lib/workflow/transitions.ts
   פונקציה טהורה אחת:
     applyTransition(request, event) -> {
       status, ownerType, ownerId, action, dueAt, escalateAt, events[]
     }
   זהו המודול היחיד בקוד שמותר לו לכתוב לשדות ה-Next Action Owner.
   הוא קורא את הדדליינים מטבלת rules — אין מספרים קשיחים בקוד.
   הוא לא נוגע ב-DB. הוא רק מחשב.

2. lib/workflow/apply.ts
   עוטף אותו בטרנזקציה: כותב את הבקשה + שורת events, באותה טרנזקציה. תמיד.

האירועים שצריך לתמוך בהם:
  REQUEST_SUBMITTED, VALIDATION_FAILED, ELIGIBILITY_FLAGGED, EXCEPTION_GRANTED,
  MATCH_PROPOSED, COORDINATOR_APPROVED_MATCH, HOLD_PLACED, HOLD_EXPIRED,
  CLIENT_CONFIRMED, CLIENT_DECLINED, PAIR_PARTNER_CONFIRMED, PAIR_PARTNER_DECLINED,
  BRIEF_STARTED, BRIEF_SENT_TO_CLIENT, BRIEF_APPROVED, BRIEF_CHANGES_REQUESTED,
  BRIEF_SENT_TO_SUPPLIER, T1_CONFIRMED, T1_MISSED, SHOOT_COMPLETED,
  DELIVERABLES_UPLOADED, DELIVERABLES_OVERDUE, DELIVERABLES_FORWARDED,
  CLIENT_CANCELLED, SUPPLIER_CANCELLED, REQUEST_CLOSED

כתוב מבחני יחידה table-driven שמכסים כל מעבר, כולל:
  • כל ארבעת המקרים של כלל האישור המזווג (ראה CLAUDE.md — קרא אותו שוב, זה קריטי)
  • hold שפג בלי אף אישור
  • hold שפג עם אישור אחד מתוך שניים
  • ספק עם accepts_solo_half_day=false שרק לקוח אחד אישר → חייב לייצר incident, לא להחליט
  • ניסיון להשאיר בקשה פתוחה בלי owner → חייב לזרוק

אל תבנה שום מסך, שום route, שום קומפוננטה.
```

**קריטריון קבלה:** `pnpm test` ירוק, ≥25 מקרי מבחן, כיסוי מלא של `transitions.ts`.
נסה ידנית להכניס בקשה `PENDING_MATCH` בלי owner — ה-DB חייב לדחות.

## פאזה 1 — Intake + מסך החריגים

```
בנה שני מסכים בלבד, מעל מכונת המצבים הקיימת:

1. טופס בקשת צילום (/requests/new) — למנהל סושיאל.
   ולידציה בצד השרת עם zod. בקשה חסרה לא נכנסת ל-PENDING_MATCH — היא נכנסת
   ל-MISSING_INFO עם רשימת החוסרים והבעלות חוזרת למגיש.
   בודק זכאות (השדה, לא מנוע): NEEDS_CHECK או NOT_ELIGIBLE → owner=COORDINATOR,
   action=GRANT_EXCEPTION.

2. מסך החריגים (/) — המסך הראשי של נועם.
   הוא קורא מה-view בשם exceptions. אל תבנה טבלת alerts.
   לכל שורה: מה קרה · אצל מי תקוע · כמה ימים · חומרה · הפעולה המומלצת · כפתור.
   הפעולה המומלצת מגיעה מ-lib/workflow/suggestions.ts — מיפוי דטרמיניסטי
   מ-(status, action) להצעה + כפתור. בלי AI. בשלב הזה זה if/else, וזה בסדר גמור.

3. db/seed.ts שמייצר 6 חריגים: hold שפג · חצי יום שהתפנה · בריף מאחר ·
   T-1 לא מאושר · תוצר באיחור · בקשה תקועה 3 ימים.

UI בעברית, RTL. מחרוזות ב-lib/i18n/he.ts בלבד.
```

**קריטריון קבלה:** אחרי seed, מסך החריגים מציג 6 שורות עם 6 הצעות שונות. לחיצה על כל כפתור מבצעת מעבר תקין.

## פאזה 2 — ספקים, זמינות ו-Soft Holds

```
1. CRUD ספקים (יכולות, אזורים, accepts_solo_half_day, SLA).

2. קישור זמינות לצלם (/s/[token]):
   • signed token, purpose=SUPPLIER_AVAILABILITY, שומרים hash בלבד
   • מובייל-first. לוח שנה. הצלם מסמן ימים פנויים ל-3 שבועות קדימה.
   • ג'וב שבועי (ראשון בבוקר) ששולח את הקישור לכל ספק פעיל.
   → זה מה שמייתר את הסבב הראשון של ההודעות. זמינות נאספת מראש, לא בתגובה לבקשה.

3. Soft holds:
   • placeHold(supplierDayId, hours) — מטבלת rules
   • ג'וב כל 5 דקות שמשחרר holds שפגו ומפעיל HOLD_EXPIRED
   • הג'וב חייב להיות אידמפוטנטי. הרץ אותו פעמיים בבדיקה — התוצאה זהה.

4. הפעל RLS. כתוב בדיקה: connection של ספק A שולף supplier_days →
   חייב להחזיר אפס שורות של ספק B. בדיקה זו חייבת להיכשל אם מישהו מכבה RLS.
```

**קריטריון קבלה:** בדיקת RLS עוברת. `HOLD_EXPIRED` משחרר ומחזיר את הבקשה ל-`PENDING_MATCH`. הרצה כפולה של הג'וב לא יוצרת כפילויות.

## פאזה 3 — Matcher + קישור בחירת מועד ⭐ הפיצ'ר המרכזי

```
1. lib/matching/matcher.ts — greedy + scoring. בלי solver, בלי PostGIS.
   סינון קשיח: יכולת הצלם · אזור · זמינות · חלונות הזמן של הלקוח ·
                זמן נסיעה ≤ rules.max_pairing_travel_minutes (haversine)
   ניקוד:  40×מזווג + 25×דחיפות + 20×(1−מרחק מנורמל) + 15×גמישות נמוכה של הלקוח
   כל מועמד מחזיר reason בעברית — נועם חייבת להבין למה המערכת הציעה את זה.

2. נועם מאשרת שיבוץ → HOLD על יום הספק כולו (שני החצאים אם מזווג).

3. קישור בחירת מועד (/c/[token]) — מובייל, בלי חשבון:
   • rules.slot_options_per_client אפשרויות + "אף מועד לא מתאים"
   • נשלח למנהל הסושיאל אם is_social_managed, אחרת ישירות ללקוח
   • שני הלקוחות של יום מזווג מקבלים במקביל
   • בחירה → CLIENT_CONFIRMED, שאר ההצעות → SUPERSEDED

4. ממש את כלל האישור המזווג בדיוק כפי שכתוב ב-CLAUDE.md.
   כשחצי יום מתפנה: הרץ את ה-matcher על החצי הפנוי בלבד וצור incident
   עם proposed_resolution שמכיל את המועמדים.
```

**קריטריון קבלה:** התרחיש המלא: 2 לקוחות → הצעה מזווגת → אחד מאשר, אחד לא → **המאשר נשאר מאושר**, חצי יום פנוי, חריג עם מועמדים אצל נועם. זה התרחיש שקובע אם המערכת עובדת.

## פאזה 4 — בריף, T-1, תוצרים

```
1. בריף: תבנית לפי סוג צילום, גרסאות, אישור לקוח ב-/c/[token].
   גרסה מאושרת = immutable. נשלחת אוטומטית לצלם.
   דדליין = תאריך צילום − rules.brief_lead_days. איחור → תזכורת → הסלמה.

2. T-1: ג'וב יומי. שולח לצלם קישור עם כפתור אחד: "דיברתי עם הלקוח".
   לא נלחץ עד rules.t_minus_1_deadline_hour → T1_MISSED → חריג אצל נועם.

3. תוצרים: הצלם מסמן "בוצע" → SLA מתחיל.
   מעלה קישור Drive + מסמן מה הועלה. אנחנו לא מאחסנים וידאו.
   עבר ה-SLA → DELIVERABLES_OVERDUE → חריג.
   הועלה → מועבר אוטומטית למנהל הסושיאל / ללקוח → הבקשה נסגרת → הזכאות נגרעת.

4. Timeline בעמוד הבקשה: קורא מ-events. כולל אפשרות להוסיף הערה ידנית
   (שיחת טלפון, הודעת וואטסאפ) — נועם צריכה מקום לשים הקשר שלא עבר במערכת.
```

**קריטריון קבלה:** מריצים את קריטריון הקבלה מ-`MVP-SPEC.md §8` מקצה לקצה. כל 10 השלבים.

## שלוש טעויות שיהרסו את הפרויקט

1. **לדלג על פאזה 0.** מכונת המצבים בלי בדיקות = באגים שיתגלו מול צלמים אמיתיים, ואז מאבדים את האמון של נועם ואי אפשר להחזיר אותו.
2. **לתת ל-Claude Code לבנות הכל בפרומפט אחד.** תקבל קוד שנראה נכון ושאף אחד לא סקר. פאזה-פאזה.
3. **להתחיל מ-AI.** אם הסוכן נכנס לפני שיש מידע מובנה ופעולות מוגדרות, הוא יהיה דמו מרשים שלא עושה כלום.

## שאלות שצריך לשאול את נועם לפני פאזה 3

אלה נכנסים ל-`rules` — אבל צריך ערך התחלתי אמיתי:

1. כמה ימי צילום בחודש? כמה צלמים פעילים?
2. **האם צלם באמת יכול לצלם 2 לקוחות ביום (8 שעות בפועל)?** אם לא — פיצ'ר הזיווג נראה אחרת לגמרי.
3. אילו צלמים לא יסכימו לחצי יום סולו? (`accepts_solo_half_day`)
4. "אזור גיאוגרפי" — לפי מה? ערים? זמן נסיעה? מה הסף הסביר?
5. מה ה-SLA האמיתי להעברת תוצרים היום, ומה היא רוצה שיהיה?
6. כמה זמן סביר להחזיק סלוט של צלם? (48 שעות זה ניחוש)
7. מי מוסמך לאשר יום צילום ללא זכאות — היא לבד?
